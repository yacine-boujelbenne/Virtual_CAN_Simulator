# ADR-001: native application, clock and world contracts

Date: 24 October 2026. Task: PLAN-00. Status: proposed for independent review.
This is a normative design for subsequent tasks, not an implemented API or a
claim of a successful native desktop, world backend or driving experiment.
After independent acceptance, changes to these boundaries require a reviewed ADR
amendment and compatibility evidence before dependent implementations diverge.

## Units and coordinate convention

Use C++20 explicit strong types, with no implicit conversion between quantities.
The names below denote distinct types, even where their storage is identical.
Validate finiteness, ranges and checked integer arithmetic at input boundaries.

| Type | Representation and meaning |
| --- | --- |
| `SimTimeUs` | Unsigned 64-bit integer microseconds since the current epoch began |
| `DurationUs` | Unsigned 64-bit duration; distinct from an absolute time |
| `EpochId`, `TickId`, `CommandId`, `JobId`, `FrameSequence` | Distinct unsigned 64-bit identities; never floating-point timestamps |
| `Metres`, `MetresPerSecond`, `MetresPerSecondSquared` | Finite doubles in SI units |
| `Radians`, `RadiansPerSecond`, `InverseMetres` | Finite doubles for angle, angular rate and curvature |
| `Newtons`, `NewtonMetres` | Force and torque when the selected plant supports them |
| `ByteCount`, `CpuCycles` | Checked integer resource quantities, separate from host process measurements |
| `NormalisedDemand` | Finite dimensionless value with bounds defined by its channel |

`SimTimeUs + DurationUs` yields a time; the difference of ordered times within one
epoch yields a duration. Reject overflow, negative differences, zero step duration
and cross-epoch subtraction. Host durations use separate steady-clock types and
must never populate simulation envelope timestamps. Convert seconds only at a
backend boundary, retaining the authoritative integer time.

Core world coordinates are right-handed: +Z up, +X along the scenario's initial
forward axis, +Y left. Position is in a fixed scenario frame, not a rotating body
frame. Body +X is forward and body +Y left. Yaw is positive counterclockwise about
+Z, zero along world +X, wrapped to `[-pi, pi)` for published state and errors.
Positive front road-wheel angle steers left; steering-wheel angle is a separate
quantity. Velocity names specify world/body frame and signed versus magnitude.
Pitch/roll or lateral dynamics unsupported by a plant are explicitly unavailable,
not invented zeros. Scenario origin, backend transform and vehicle dimensions
belong in backend configuration and the run manifest. Test transform round trips
and a known left turn before claiming backend integration.

Legacy adapters convert existing km/h, milliseconds, degrees or wire scalings at
their boundaries. They retain existing JSON keys and CAN bit layouts; adopting SI
internally must not silently reinterpret stored project values.

## Application boundary and ownership

One `ApplicationService` owns run lifecycle, the logical clock, active project,
ECU registry, broker, selected ego authority and recorder. Only its serialized
simulation execution context mutates them. Qt and web clients submit commands
and receive immutable snapshots; they never advance the clock or call a plant.
HTTP dispatch uses one isolated worker/container per declared ECU. Missing workers
pause the barrier with an explicit error; no implicit embedded-worker fallback.
An explicitly selected embedded development profile retains its existing label.

| Contract | Required content and behavior |
| --- | --- |
| `CommandEnvelope` | Command ID, expected epoch, requested simulation boundary and typed payload; host receipt time is separate metadata |
| `CommandResult` | Command ID, accepted/rejected/applied state, effective boundary and structured error; enqueue acceptance does not mean physical application |
| `submit(CommandEnvelope)` | Enqueue without waiting for physics on the UI thread; validate again at the application boundary |
| `snapshot()` | Immutable coherent `ApplicationSnapshot` from the last committed boundary; includes epoch, tick, simulation time, run state, project hash, selected profiles, world/ECU/observations and integrity status |
| `prepare(TickIdentity)` | Freeze inputs and eligible commands once; same identity returns the same logical request on retry |
| `complete(TickIdentity, WorkerResults)` | Validate all identities/results before committing; missing/invalid results do not advance time |
| Project service | New/Open/Save/import/export validation and transactional application belong in C++; an invalid import preserves the active project |

`TickIdentity` contains epoch, tick and the frozen request identity. A worker retry
uses that same identity and payload; different content under that identity is a
conflict. Cache completed results until their barrier is committed or epoch is
retired. Reject unknown, duplicate conflicting, stale-epoch and future results.
Commands arriving after prepare wait for a later boundary. Reset is serialized,
increments the epoch, cancels queued jobs/frames, fences old replies and resets
all selected authorities together. Commands targeted at a retired epoch fail.

CORE-00 must first expose the current prepare/complete semantics unchanged. The
stronger cross-tick scheduling and cancellation semantics below activate through
TIME-00 with an explicit profile and regression evidence, not as a refactor side
effect. Keep Python launchers/oracles available during transport parity work.

## Clock, jobs and causality

One clock authority chooses fixed `dt` from the active configuration and owns
`t = tick * dt` with overflow checks. Renderer cadence, wall-clock pacing, HTTP
timeouts and host CPU throttling do not alter simulated time or virtual task cost.
The compatibility profile retains the current 10 ms default and configured step.

In the resource-aware profile, `JobEnvelope` carries epoch/job/ECU/task identity,
input snapshot identity, acquisition/release/start/finish times, deadline,
resource reservation and result state. Inputs remain immutable throughout a job.
Use states queued, running, completed, cancelled, deadline-failed and
resource-rejected. Queue/RAM/flash reservations are bounded and released exactly
once. CPU budgets, watchdog policy and pending job state are part of the modeled
ECU, distinct from actual container resource metrics.

A job may span ticks. It publishes only at modeled completion; no frame is
eligible for transmission before `computed_at_us`. A barrier retry cannot rerun
or mutate an already completed job. An old-epoch completion cannot publish into
the new epoch. Deadline failure, queue saturation and watchdog reset have explicit
recorded outcomes and configured recovery. Do not clamp a long computation to
fit the tick or forge an early completion.

Each observation retains its original acquisition timestamp, validity and reason,
source/sequence and any computed/received/observed timestamps. Missing acquisition
time is unknown freshness, never implicitly fresh. At a consumer boundary,
`age = observed_at - sampled_at` within the same epoch; reject future acquisition
time. Delayed reception does not renew acquisition time. Consumers use declared
validity/age thresholds and an explicit fallback, never substitute ground truth.
Existing freshness behavior remains a documented debt until TIME-00 passes.

Enforce ordering only for timestamps that exist on the same causal chain:
sampled <= computed <= received <= observed <= applied. Frames and jobs without
an actuator do not invent an applied timestamp. Distinguish broker scheduling,
wire delivery and consumer observation; reuse the existing v2 envelope adapter
without falsely claiming the JSON Schema itself proves arithmetic ordering.

## WorldFrame, ego authority and step order

`WorldFrame` is an immutable value containing epoch/tick/time, scenario coordinate
frame ID, backend identity/version, ego truth pose/velocity, non-ego actor states
with stable IDs, and optional road/environment facts with validity. It is a truth
boundary for sensors, rendering and evaluation. A separate `ObservedVehicleState`
contains measured/estimated pose and velocity, acquisition time, validity/age and
source identities for controllers. A controller does not receive `WorldFrame`.
An ideal-localization experiment must be explicitly selected and recorded.

`IWorldBackend` exposes capability/configuration validation, initialize/reset,
read-only current frame, one fixed-step advance and shutdown. Configuration pins
backend version, asset/scenario identity, ego actor ID, transform, authority mode
and supported sensor/step capabilities. Return structured unavailable/invalid/
step-failed results; do not silently substitute a stub for a requested 3D backend.

The backend advance accepts a step identity, start/end simulation times and the
authority-specific input. In external-ego mode it receives the plant's committed
ego pose; in backend-physics mode it receives ECU-arbitrated actuator demands.
The result is a WorldFrame correlated to that exact epoch and end time. Reject
mismatched timestamps and duplicate conflicting step identities. A renderer
cannot call advance. An external engine failure after physical advancement fails
the run and requires synchronized reset; do not retry that engine step blindly.

The logical interval from `t` to `t + dt` has this order:

1. Read the committed truth/world frame at `t`; freeze eligible commands and
   sensor acquisitions, plus previously eligible delivered frames.
2. Dispatch frozen ECU work. Account for modeled job completions and broker
   events in causal order. Completed outputs may enter CAN after their computed
   time; consumers observe them at their declared observation boundary.
3. Validate the complete barrier and arbitrate Motor/ABS/EPS/transmission output.
   Retain one binding owner per actuator, brake inhibit and bounded requests.
   Driver and tracking demands traverse the declared ECU/CAN route.
4. Advance the sole ego physics authority and world exactly once, producing the
   frame at `t + dt`. In external-ego mode integrate the C++ plant then synchronize
   its pose while advancing non-ego actors. In backend-physics mode advance the
   backend using actuator demands; the internal ego integrator is disabled.
5. Correlate recorder entries and publish the coherent snapshot/time only after
   successful completion. Failure preserves the last committed snapshot and
   exposes a failed/paused run; it never publishes partial success.

The P0 compatibility profile preserves its tick-boundary actuation timestamps and
frame/envelope signatures. This ADR does not promise finer actuator resolution or
reinterpret the historical applied timestamp. A later profile that changes the
physical application interval must name and test that temporal semantics change.

| Profile | Clock owner | Ego physics owner | World responsibility |
| --- | --- | --- | --- |
| Headless/null | ApplicationService | Internal C++ plant | Deterministic scenario/environment data; labelled headless |
| esmini external ego, first 3D target | ApplicationService | Internal C++ plant | Roads/non-ego actors/viewer; conflicting ego controllers disabled |
| Optional CARLA replacement physics | ApplicationService with sole synchronous tick ownership | CARLA | Fixed-step ego/scene physics and declared sensors; internal ego plant disabled |

WORLD-00 must pin and probe the installed esmini library and verify external ego,
coordinate conversion, reset and one advance per tick before WORLD-01 integrates
it. Start with a separate native viewer window; embedding requires separate
evidence. A null backend is suitable for headless tests, not 3D acceptance.
The optional CARLA profile declares fixed step, substeps, sensor acquisition
periods and frame correlation, and rejects a second tick owner. SDK signatures,
supported hardware and deterministic scope require a later capability gate.
CarSim remains an optional licensed future backend under the same single-ego
rule; no commercial backend is required by these interfaces.

## Recorder and compatibility

`RunRecorder` accepts immutable correlated event batches, reports queue capacity
and integrity, and supports flush/finalize. Reserve capacity before advancing a
required recording interval where feasible. Saturation or I/O failure latches
integrity failure and pauses/aborts according to the run profile. Never silently
drop records and still report a valid experiment. A crash or unfinished manifest
remains incomplete; only successful finalization marks clean close.

The manifest binds exact project hash, source/build identifiers, backend/asset
versions, controller/resource profiles, seed, step, coordinate transform, time
semantics and integrity outcome. Record full-run events/CAN/trajectory/controls/
performance with epoch and sequence correlations, separating truth, observations
and reference trajectory. Bounded snapshot windows are not durable logs. LOG-00
implements this seam; REPLAY-00 separately defines replay source and determinism.

Preserve actual single-JSON `.vcanproj` schema v1 and C++ canonical SHA-256 over
`{scenario, ecu_definitions, can_map, run}`. Runtime controls/time and UI state
stay outside that hash. Retain derived CAN-map validation, transactional import,
strict declared-hash rejection and the existing A/B frames-plus-envelopes fixture.
CORE-00 adds no serialized defaults or fields that change the canonical content.
PROJECT-00 must define and test any versioned extensions/migration for native
controller, resource or backend configuration. Do not activate an unpersisted
parameter silently; include selected runtime profiles in the manifest and label
the run until project persistence is supported.

Headless builds must isolate optional Qt and 3D dependencies. CLI, desktop and web
adapters use the same service, project and snapshot contracts. Production native
execution eventually removes Python orchestration through CORE-01/CORE-02;
Python remains supported for oracles, analysis and development coordination.

## Acceptance consequences

This ADR's configured check is `python3 tools/validate_coordination.py`; it validates
the coordination pack, not these future APIs or physical behavior. Independent
review must check units, causal boundaries and compatibility against LAW and the
actual P0 source. Subsequent task evidence must cover at least:

- Unchanged P0 hashes, vectors and frame/envelope signatures during extraction.
- Frozen retry inputs, conflicting duplicates, missing workers and reset fencing.
- Delayed acquisition age, cross-tick completion, queue/RAM bounds and watchdogs.
- One plant/world advance, transforms, reset and explicit backend unavailability.
- Controllers using observations and ECU/CAN requests, preserving actuator owners.
- Recorder saturation, partial/crash versus clean close and manifest correlation.
- Headless dependency isolation and UI snapshots without physics on the UI thread.

Passing mock/headless checks does not establish a real viewer, container recovery,
calibrated hardware profile or deterministic external-engine physics. Each such
claim needs the corresponding task's independently accepted execution evidence.
